# 伞伴智能雨伞产品方案说明（V4.1 · 学生项目版）

> 本文在 V4 精简版基础上调整：**商业模式 → 价值假设与验证方式**；**实施路线 → 学期可完成路线**。  
> 本阶段以学习与验证为主，不开展真实收费与规模化运营。

---

## 一、方案概述

「伞伴」首先是一把好用的伞，其次才是一把不容易丢的伞。产品以成熟防丢模块为安静内置能力，以轻触点（小程序 / 网页原型）连接用户，围绕「忘带伞」和「伞总丢」两个痛点提供服务闭环。

与已有智能伞相比，差异化在于：**主动是后台的可靠执行，不是前台的持续表演；订阅是丢失后的安全网，不是贯穿全程的商业主线。** 买伞时不强调订阅，日常使用不推销服务，未订阅用户享有完整基础功能。

**学生项目补充定位：** 本学期交付「产品方案 + 可交互原型 + 真伞最小硬件验证 + 过程仓库」，不承诺量产、上架商用小程序或真实收款。

---

## 二、设计哲学

- **好伞是 1，智能是后面的 0。** 伞面、骨架、握感、重量是底线，不因智能化妥协。
- **主动性是隐性可靠，不是显性汇报。** 用户感知到的是「需要时恰好准备好了」，而非「它一直在告诉我它很忙」。
- **服务按需浮现，从不制造焦虑。** 订阅仅在失物模式中作为平等选项之一呈现，无高亮、无推荐。

---

## 三、用户与痛点

目标用户：城市通勤族、学生及经常丢三落四的人群。

- **忘带伞：** 「带还是不带」的决策负担 → 结合天气与出行习惯提醒，用户不必时刻查天气。
- **伞总丢：** 「又丢了」的挫败感 → 防丢检测 + NFC 送回 + 丢后兜底选项，挫败感被服务接住。

---

## 四、总体架构

| 层级 | 内容 | 本学期落地方式 |
|------|------|----------------|
| 伞体硬件 | 好伞 + BLE + 蜂鸣器 + LED + NFC + CR2032，IP67 为目标 | 真伞 + 市售 BLE 标签 / NFC 贴纸做最小验证；IP67 不宣称已达成 |
| 智能体服务 | 端侧常驻点与提醒抑制；云端天气、位置快照、订阅 | 以网页原型模拟流程；不做真实云端商用 |
| 轻触点 | 小程序绑定 / 寻伞 / 设置；通知推送 | 以 HTML 原型演示；小程序上架列为远期 |

---

## 五、核心功能

### 5.1 基础能力（所有用户默认可用）

- **首次绑定引导：** 3 步建立认知锚点（好伞 → 防丢 → 提醒），之后不再重复展示。
- **安静防丢：** 离开常驻点且伞未随行时自动提醒；常驻点内分离不打扰。界面仅显示「伞已连接 · 防丢就绪」。
- **提醒硬上限：** 同类提醒每日 ≤2 次；标记「不准」后暂停 24h；连续 3 次忽略自动降级为静默记录；22:00–07:30 免打扰。
- **位置记忆：** 断连时记录最后位置快照（**非实时追踪**，文案必须标明）。
- **声光寻伞：** 蜂鸣器 + LED 快闪，20 秒自动停止。
- **NFC 匿名送回：** 贴纸 + NFC + 二维码；**电池耗尽后 NFC 仍有效**（无源）。
- **天气带伞提醒：** 结合天气与出行习惯推送，一键确认消除当日重复提醒。
- **常驻点学习：** 端侧聚合，候选地点需用户确认；可修改 / 暂停 / 清除。
- **电量管理（四级）：**

| 电量 | 行为 | 用户感知 |
|------|------|----------|
| >30% | 静默运行 | 无打扰 |
| 15–30% | 提示卡片 + 有限次数消息 | 温和提醒 |
| 5–15% | 降低蓝牙频率，暂停非关键 LED | 功能降级，核心防丢可用 |
| <5% | 仅保留位置记录 + NFC，关闭蜂鸣器 | 明确告知暂停的功能 |

### 5.2 雨天应急协助（所有用户可用）

按距离 / 安全性排序：就近避雨 → 借用共享伞 → 安全回家 → 联络助手。所有外部操作需用户确认。

**联络助手安全机制：** 长按 2 秒 → 短震 → 二次确认 → 10 秒倒计时（可取消）。统一免责：「仅辅助联络，不替代专业救援。紧急情况请拨打 110/120。」

### 5.3 可选兜底服务（按需浮现 · 远期）

仅在失物模式点击「看看还有什么选项」后，作为平等选项呈现，例如：

| 借用共享伞 | 购买同款 | 了解兜底服务 | 暂时不处理 |
|------------|----------|--------------|------------|

订阅详情需再点一层，并声明：可选、不含在售价中、未订阅不影响基础功能。  
**本学期只演示交互与收集付费意愿，不实现真实订阅履约。**

## 六、硬件与技术路线

- **伞型：** 半自动（一键开、手动收）与手动两种；半自动电子模块在伞柄中下部，避开弹簧空间。不加线性马达、机械鳍片、温湿度传感器。
- **智能模块：** BLE + 蜂鸣器 + LED + NFC + CR2032。
- **结构目标：** 伞杆与伞柄可拆卸，便于换面续用；电子仓与弹簧通道物理分隔；外壳以密封无开孔为方向（IP67 为待测目标，未实测不宣称）。

### 定位能力：诚实边界（本学期必须遵守）

本产品**没有**「伞上实时 GPS / 地图上一直跟着走」的能力。对外与答辩口径统一如下：

| 层级 | 实际含义 | 大致可达范围 | 本学期 |
|------|----------|--------------|--------|
| 近场声光寻伞 | 手机与伞上 BLE 仍连接时，触发蜂鸣 / LED | 常见白牌标签约 **10–30 m**（室内更短；空旷偶可达数十米） | ✅ 演示 / 真标签实测 |
| 断连位置快照 | 记录断连瞬间**手机**的位置，不是伞的坐标 | 与「伞离你多远」无关；伞被带走后**不再更新** | ✅ 原型文案必须标明 |
| 远场查找 | 见下节「如何更远」 | 可达城区～更广，视方案而定 | ❌ 本学期不实现、不宣称已具备 |

**禁止表述：** 「实时定位伞」「最远定位 X 公里」「GPS 追踪伞」。  
**正确表述：** 「最后出现位置 = 断连时的手机位置」；「近场靠蓝牙声光；更远依赖远期能力，本学期未交付」。

### 如何更远（远期路线，非本学期交付）

在坚持「好伞优先、CR2032、密封少开口」的前提下，拉远查找能力只能换链路，不能指望把现有 BLE 吹成远距定位：

| 优先级 | 做法 | 能远到哪 | 代价 / 前提 |
|--------|------|----------|-------------|
| 1（小改） | 优化近场：更好天线 / 短时提高发射、选支持较远距离的 BLE 标签 | 仍多在 **几十米级** | 耗电上升；仍非追踪 |
| 2（体验） | 断连瞬间多采几次手机位置（Wi‑Fi / 基站辅助） | 不增加伞的距离，只让「最后点」更准 | 隐私说明要清楚 |
| 3（推荐远期） | **接入找物网络 / 众包**（类 AirTag：陌生设备匿名上报大概位置） | **城区～更大范围** | 需生态或自建后端、合规与隐私设计 |
| 4（重路线） | 伞上蜂窝（LTE-M / NB-IoT）+ GNSS | **公里～全球** | 大电池或充电、天线窗、月费；与扣电密封手柄冲突大，本项目不作为默认 |

**本学期结论：** 验证近场分离提醒与寻物 + 把边界写清楚；把「更远」明确写成 **远期优先考虑找物网络（众包）**，不在本学期硬件上做 GPS/蜂窝。

### 电池与续航策略

坚持 CR2032，不引入潮湿环境下的充电接口。思路不是「电池绝对更耐用」，而是**用户永不缺电**：

| 层级 | 措施 |
|------|------|
| 默认 | 随伞附赠 1 颗备用 CR2032 |
| 体验 | 免工具旋转仓 + 型号刻印 + 短视频教程 |
| 远期可选 | 订阅用户年度寄送电池；小程序引导购买备用电池 |

12–18 个月续航与 IP67 均为**设计目标**，须样机实测后才能宣称。

### 本学期硬件最小路径

1. 选一把好用的普通伞；  
2. 加装市售 BLE 防丢标签；  
3. 加贴 NFC / 二维码归还说明（可先用占位链接）；  
4. 完成分离提醒与寻物实测并留照片 / 日志。

## 七、数据架构与隐私

| 数据类型 | 存储 | 加密 | 保留 | 删除 |
|----------|------|------|------|------|
| 原始 GPS 轨迹 | 仅端侧，永不上传 | 系统级 | 不长期保留 | 清除学习数据时删除 |
| 常驻点标签 | 端侧为主 | TLS1.3 + AES-256 | 至用户删除 / 注销 | 一键清除 / 注销 |
| 位置快照 | 云端（远期） | TLS1.3 + AES-256 | 基础 7 天 / 订阅 90 天 | 自动过期 / 手动 |
| 设备绑定 | 云端（远期） | TLS1.3 + AES-256 | 至解绑 / 注销 | 解绑即删 |
| NFC 消息 | 云端中转 | TLS1.3 | ≤24h | 送达即删 |

最小权限：附近设备、位置、通知。日程 / 通讯录 / 实时位置为可选。  
**当前原型阶段所有数据均为本地模拟，不涉及真实上传。**

## 八、价值假设与验证方式（原「商业模式」调整）

### 8.1 本阶段定位

学生项目阶段**不设收入目标**。重点验证：

1. 是否接受「先是好伞，其次才是智能」；  
2. 「安静防丢 + 最后出现位置」是否好懂、是否够用；  
3. 丢后兜底是否有人愿意付费（只测意愿，不收款）。

### 8.2 价值假设

| 假设 | 内容 | 如何验证 |
|------|------|----------|
| H1 好伞优先 | 用户更在意伞好不好用 | 方案与原型是否体现「好伞优先」 |
| H2 安静防丢有用 | 有限提醒优于频繁推送 | 提醒规则与上限是否可演示 |
| H3 非实时定位可接受 | 理解「最后位置 ≠ 实时追踪」 | 文案与失物页是否标明边界 |
| H4 订阅非必买 | 基础功能不依赖订阅 | 失物页选项是否平等、无推销高亮 |
| H5 远期收费可能成立 | 硬件利润 + 可选服务 | 本学期仅保留设想，不作验证结论 |

### 8.3 远期商业设想（附录）

若未来真实试点成立，可考虑：

- 硬件合理利润定价（非补贴）  
- 失物场景可选年费（如 ¥99/年）  
- 备选：换面、企业定制、按次增值  

**本学期明确不做：** 真实支付、订阅履约、规模获客、单位经济拍板。

### 8.4 本阶段交付

- 可演示的方案与交互原型（含模拟边界说明）  
- 真伞最小硬件验证记录（分离提醒 / 寻物）  
- 复盘材料：完成度说明、过程日志、答辩讲稿

## 九、学期实施路线（原「实施路线」调整）

### 9.1 本学期三阶段

| 阶段 | 时间 | 重点 | 完成标准 |
|------|------|------|----------|
| A 概念与原型 | 第 1–2 周 | 方案入库、HTML 原型、测试记录 | 核心流程可点通，模拟边界写清 |
| B 真伞最小验证 | 第 3–5 周 | 真伞 + BLE 标签安装与实测 | 分离提醒、寻物各至少成功 1 次并留证 |
| C 复盘答辩 | 最后 1 周 | README、过程日志、讲稿 | 能分清已做 / 模拟 / 下一步 |

**提交原则：** 每完成一小步就 Git 提交一次，保留时间线，避免期末一次性上传。

### 9.2 学生版验证指标

| 维度 | 指标 | 目标 |
|------|------|------|
| 原型可演示 | 引导 / 防丢 / 寻伞 / 电量 / 失物流程可点通 | 全部走通并留测试记录 |
| 概念边界清晰 | 文案标明「非实时定位」与模拟项 | README 与原型均可见 |
| 硬件可行 | 分离提醒与寻物可复现 | 各 ≥1 次成功记录 |
| 过程可证明 | Git 提交与过程日志 | 有清晰时间线 |

### 9.3 结项决策

| 观察 | 结论 |
|------|------|
| 原型清楚、硬件最小验证成立 | 概念可继续打磨；订阅仍为远期选项 |
| 硬件验证困难 | 保持市售标签路径，缩小宣称范围 |
| 文案易误解定位边界 | 先改提醒规则与「最后出现位置」表述 |

### 9.4 远期产品路线（附录 · 非本学期 KPI）

| 阶段 | 周期 | 重点 |
|------|------|------|
| MVP | 0–3 月 | 防丢标签 + 小程序 |
| 试点 | 3–6 月 | 一体伞样机 + 种子用户 |
| 服务化 | 6–12 月 | 再决定订阅上线 / 调整 / 暂缓 |

## 十、风险与应对（学生项目口径）

| 风险 | 应对 | 本学期验证 |
|------|------|------------|
| 被当成「只会闪的电子伞」 | 强调好伞优先；引导三步认知 | 引导与方案表述是否到位 |
| 提醒令人烦 | 硬上限 + 免打扰 + 负反馈降级 | 提醒规则可在原型中演示 |
| 被误解为实时追踪 | 文案固定写「最后出现位置」 | 失物页与 README 边界说明 |
| 硬件做不完 | 采用市售标签，不自研主板 | 实测日志与照片 |
| 过程无法证明 | 多次 Git 提交 + process_log | 仓库提交时间线 |
| 应急责任边界 | 二次确认 + 免责声明 | 原型中保留安全流程 |

## 十一、结语

**让用户忘记这是一把智能伞，只记得这是一把好伞。**

好的管家不会每隔十分钟汇报他做了什么。你只在需要时发现：该带的带了，落下的找得回，丢失后还有退路。

伞伴要做的，就是这样一个靠谱的管家。  
对学生项目而言：先把「靠谱」验证清楚，再谈规模化与收费。
